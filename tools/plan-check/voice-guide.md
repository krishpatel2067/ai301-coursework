## Who I am in threads

<!-- 2-3 lines. Who is talking when you comment on an issue: your

I mention my experience level (e.g., "as a first-time contributor", etc.) to give the maintainers a heads-up. I state my intention in choosing this repo for my contribution (e.g., "I'm intimately familiar with this library as a user", etc.). I express what others can expect from me in the future (e.g. "my next steps:", "will follow up soon", etc.).

### Rule: Be Concise

Maximize info-to-syllables ratio. If there's a shorter, more direct way to write something (without sounding rude), write it that way. Air-tight grammar isn't the goal: use fragments when full sentences aren't necessary.

- Wrong: "The library utilizes this function in order to generate a list."
- Right: "The library uses this function to generate a list."
- Reasoning: "Utilize" and "use" mean the same thing, but the latter is shorter. Same for "in order to" and "to".

- Wrong: "I will follow up soon with the reproduction after I set up the repository."
- Right "Will follow up soon with the repro after I set up the repo."
- Reasoning: "I" isn't necessary since it's implied that the post's author is the one who will follow up. "Repository" and "reproduction" don't need to be spelled out completely if their equally-intelligible counterparts, "repo" and "repro", exist.

### Rule: Lists Over Paragraphs

Whenever a paragraph exceeds 5 sentences, split it up into multiple paragraphs or use a bulleted/numbered list. Also, if a paragraph's content (no matter how little) is inherently list-like, use a list with repetitive/unnecessary info removed.

- Wrong: "First, I ran the server using the command stated in the issue. Then, I checked whether the server was running by executing this script. Next, I launched the frontend locally using the command above. Fourth, I clicked through the frontend to get to the state when the bug occurs. Finally, I triggered the bug, checking on the backend too."
- Right: "1. I ran the server using the command stated in the issue.
2. Checked whether the server was running by executing this script.
3. Launched the frontend locally using the command above.
4. Clicked through the frontend to get to the state when the bug occurs.
5. Triggered the bug, checking on the backend too."
- Reasoning: This is inherently a step-wise process, so a numbered list makes more sense and is more readable. Also, removing the repetitive "I" from steps 2-5 makes the info read better.

### Rule: Minimal Unnecessary Qualifiers

Minimize qualifiers such as "a bit", "probably", "pretty" unless absolutely necessary.

- Wrong: "This was pretty diffcult to reproduce."
- Right: "This was difficult to reproduce."
- Reason: "Pretty" isn't needed if the issue is indeed difficult to reproduce.

### Rule: Use Contractions Appropriately

Use English contractions ("I'll", "I can't", etc.), but sparingly. Too few contractions sounds rigid and stiff. Too many loses emphasis. A case-by-case call.

- Wrong: "I cannot reproduce this."
- Right: "I can't reproduce this."
- Reason: "cannot" sounds too stiff in this instance.

- Wrong: "Unlike the other approach, this doesn't lead to the error in question."
- Right: "Unlike the other approach, this does _not_ lead to the error in question."
- Reason: Isolating the "not" allows proper emphasis.

## Things I never post

<!-- A short list. Promises you cannot keep, tones you refuse,
shortcuts you know you reach for when tired. The skill quotes this
list back at you when a draft crosses it. -->

- Emojis (not professional usually)
- Casual text abbreviations ("idk", etc.) (not professional)
- Specific deadline (looks bad if missed)
- Anything in non-neutral tone (accusatory, gleeful, etc.) (not professional, potentially toxic)
